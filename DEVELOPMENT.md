# FluidSim development guide

The uniform CPU/GPU liquid engines implement geometric material transport and consistent mass/momentum transport. The native adaptive engine uses one project-owned 2D hierarchy and composite projection for gas and optional liquid phases. Liquid geometry, component masses and momentum share transfers through successive X/Y passes. Uniform CPU and GPU pressure default to multigrid-preconditioned CG; AMR uses the source-derived composite MAC projection. Optional surface tension remains a later stage. `VISION.md` holds the longer-term ambitions and maths; this file is the short map of the working code and possible next steps.

All engines use the component system. For the uniform liquid engines, configure the element catalogue and liquid/gas mixtures, then upload component masses alongside `liquid_fraction`, the total liquid volume fraction. Density, momentum and displayed colours come from those masses. Engine geometry uses liquid/gas terminology; Water, Red, Air and Cloud are scene ingredients. Several miscible ingredients share each phase's geometry; adding an ingredient does not add another interface reconstruction or pressure solve.

The scene catalogue contains blue Water and Red liquid, plus Air and a cyan Cloud gas ingredient. The scene's `red_share` selects the liquid blend. Air and Cloud share density 0.1. The initial atmosphere uses three Perlin scales to divide its unit gas volume between Air and Cloud. These colours are transported normally so they trace motion. Scene walls are closed, including the top. The adaptive engine advances actual coarse/fine level cells; it does not retain hidden fine material samples.

## Engine selection

The sidebar selects the actual engine; restarting preserves the scene options.

| Selector | CPU / GPU implementation |
|---|---|
| CPU uniform | `FluidGrid.h/.cpp` |
| CPU adaptive | `FluidGridAdaptive.h/.cpp` |
| GPU uniform (WebGPU) | `FluidGridGPU.h/.cpp` |
| GPU adaptive (WebGPU) | `FluidGridAdaptiveGPU.h/.cpp` |
| GPU uniform (WebGL) | `FluidGridWebGL.h/.cpp`, restored from the committed GL engine |

The adaptive CPU/GPU pair was previously named AmrGas/AmrGasGPU. Their numerical methods are retained. The uniform WebGPU transport uses the CPU's named stages (`transportStepLimit`, `freezeComponentCorrections`, `advectDirection`) while preserving GPU dispatch order. Shared state conversion lives in `FluidGridTypes.h`; GPU storage/dispatch remains private. GPU gas damping mirrors the CPU gas-only-face operation; zero disables it. The restored WebGL engine retains its original CPU coarse-pressure cutoff.

Automatic refinement and fixed fine/coarse controls apply only to the adaptive engines. A true uniform engine is selected explicitly. Headless `engine` values 0..4 follow the table; older `webgpu` settings still select the adaptive CPU/GPU pair. All engines share scene initialization and frame timing. WebGL calls/destruction run on the render thread; WebGPU stays on the simulation worker. Diagnostic GPU downloads are headless-only, outside measured updates. This organization does not establish numerical or performance equivalence between uniform and adaptive methods.

`FluidSimEngine` is a local CMake library used by both the scene and tests. It depends on Bitloop's vector type and thread pool, but has no Scene, camera, OpenGL or UI code. Another experiment can include `FluidGrid.h` and link that target. Packaging it as a separate repository is a later decision.

A new `FluidGrid(width, height, cell_size)` starts with zero velocity and zero liquid fraction. Configure its mixtures and populate component masses before advancing physics. The scene creates an initial `State` in `initializePool()` and passes it to `upload()`; that sloped pool is an experiment, not an engine default. Existing CPU public arrays and individual operations remain available for learning. Dimensions and cell size describe a fixed grid; changing them requires constructing another grid.

CPU density, pressure coefficients and the multigrid hierarchy are now cached. After directly editing `liquid_mass`, `gas_mass` or derived density/pressure-coefficient arrays, call `fluid.invalidateCaches()` before the next physics operation. It marks derived data stale; rebuilding happens when needed. `upload()` and engine material transport do this automatically. Direct velocity edits need no cache notification because CPU velocity statistics are recomputed, but transport still requires projected velocity. Mixture membership changes continue to require `upload()`. GPU buffers remain engine-owned. Its `upload()` already invalidates its caches; direct CPU-array access is not part of the shared interface.

## Current scene and engine controls

The scene selects `FluidGridAdaptive` (CPU) or `FluidGridAdaptiveGPU` (WebGPU), with the same optional liquid ingredients and adaptive policy. Scenarios 2/3 retain closed circulating Air/Cloud, no gravity, optional damping, and automatically selected fine patches over a coarse background. Scenario 2 uses the optional Perlin cloud (`perlin_clouds`, currently disabled by the user). Scenario 3 (`MOVING_CLOUD_DETAIL`) starts one compact cloud with a one-world-unit tanh edge; its centre is (.3W,.5H), radius .06 min(W,H), and circulation speed W/128. Its damping defaults to zero so the cloud travels beyond its original footprint during the 32-second comparison. Selection uses the existing tolerances and actual fields; no patch follows a prescribed trajectory. Old regions should merge as the cloud leaves. Scenarios 0/1 now use geometric liquid transport in that hierarchy, gravity 100 and closed walls. The user explicitly removed the old open atmospheric top. Automatic selection protects all liquid and its predicted halo at 1x1; only eligible gas merges. The initial liquid validation is CRASHING_WAVE at 512², maximum 4, capped at 100 frames. WebGPU numerical validation and scene integration are tracked in CURRENT_WORK; a successful compile alone is not browser acceptance. The scene owns exactly one physical engine, not an unused full-resolution copy alongside AMR.

The scene starts at full resolution so initial material detail is assessed before any merge. At intervals of at least 0.32 simulated seconds, `FluidCoarseningPreview::proposeLayout()` turns the current error decisions into buffered fine patches. Requests are quantized to tiles of max(16, parent cell width) finest cells and clustered by the source-derived 2D Berger–Rigoutsos algorithm at 70% tag efficiency. Every requested cell remains covered. If fine coverage reaches 75%, a single fine grid avoids allocating more cells than uniform. Quiet regions merge after the existing 0.24-second dwell; new resolved detail requests refinement on the next assessment. The selected maximum is 2x2, 4x4, 8x8, 16x16 or 32x32, with adjacent 2:1 levels. The current default maximum is 4x4; deeper levels are options, not a promised speedup. At each candidate width, selection assesses actual material/flow detail and its own quiet history. Each child patch is nested inside its parent with two parent cells of padding for ghost/interpolation stencils. If clustered coverage at a finer size reaches 75%, that size becomes the full-domain base and all coarser levels are dropped; 1x1 coverage at 75% selects uniform fine. There are no gravity, horizontal-cut or material-name assumptions.

A full coarse base remains stored beneath fine patches. The sidebar reports both active and allocated cells. **Adaptive grid** restarts the same scene when toggled, preserving other settings: on enables automatic fine/coarse selection; off runs the same native engine uniformly fine and skips adaptive assessment/decision overlays. **Maximum cell size** selects 2x2, 4x4, 8x8, 16x16 or 32x32 and restarts the scene. With adaptivity off, **Uniform coarse control** instead starts the entire scene at that size, conservatively averaging the same fine initial material. Fine 1x1 cells have no outline. Coarse outlines are green (2x2), amber (4x4), magenta (8x8), cyan (16x16), and red (32x32). Both mode controls restart from the original state so previously discarded detail does not contaminate comparisons. **WebGPU simulation** switches the same scene between CPU and GPU, restarting with its settings intact. Both backends support desktop and browser builds. Hiding the decision overlay alone never changes physics. The check interval and existing error tolerances remain editable, and restart preserves them. Timing includes remap/restoration in physics and reports selection separately. Cadence bounds assessment frequency, not the propagation speed of pressure; newly introduced sources cannot be predicted from old state.

Scene `projection_tolerance` defaults to `1e-3` and is independent of the pressure-gradient detail tolerance. The headless JSON option of the same name applies consistently to initial projection/upload, physical steps and regrid restoration on every backend, and traces record its value. It selects existing solver quality; AMR GMRES still uses its stricter absolute L2 target and checks actual divergence. Optional JSON `capture_stride` overrides the selected Scenario capture stride without changing physics or its default.

The scene owns catalogue/initialization, timing, layout schedule, UI and rendering. `sceneProcess()` advances physics once per scene tick. `viewportProcess()` does not advance it. Restart preserves controls and rebuilds the current initial state. `AmrGasRuntime` configures eight OpenMP workers by default; an explicit `OMP_NUM_THREADS` overrides that default. Display and preview read non-owning patch views without creating another physical state; scene scheduling must keep those reads separate from physics mutations.

`FluidCoarseningPreview` reads actual committed cells. Native gas fine groups measure material loss to the same bounded linear plane used for transport, display and refinement interpolation. Velocity compares cell momentum/density and independent MAC faces with the actual bounded regrid reconstruction, rather than requiring small variation around a constant mean. Smooth reconstructible motion can merge; unresolved child residuals, neighbour curvature and distinct adjoining fine-face samples can still request refinement. Reflecting walls and the velocity-residual limiter can retain motion detail; momentum extrema do not flatten material slopes. Ingredient fractions, relative density and pressure-gradient detail remain independent criteria. These are local representation indicators, not bounds on accumulated transport error or an oracle for discarded detail. Uniform liquid previews retain their flat-mean indicator because their transport model is unchanged.

A swept feature envelope looks ahead by at least the check interval plus one scene frame, with an additional coarse-cell spatial buffer before clustering. AMR pressure is a correction impulse divided by the last physical substep; geometric restoration has no physical pressure sample. Physical gas walls and coarse/fine joins are assessed using available neighbours. Uniform liquid previews keep their protected liquid halo and unassessed outer edge.

Only current detail/refinement indicators seed that spatial buffer. A quiet fine cell waiting for its dwell retains its own tile without requesting padding around it. This distinction prevents a newly refined buffer from repeatedly growing new buffers as its history resets. Quiet dwell, feature prediction, clustering and thresholds are otherwise unchanged.

Green means settled merge candidate, yellow retain/wait, purple liquid/buffer, grey unavailable stencil, red resolved refinement detail and orange approaching detail. Transparent fills preserve the clouds; green/amber/magenta/cyan/red outlines show the **actual** 2x2/4x4/8x8/16x16/32x32 cells; 1x1 cells have no outline. The fill is the last selection assessment, which can precede the displayed remap. Quiet history survives in unchanged regions; an exact shared byte map of actual sizes per 2x2 footprint resets only affected groups, without a packed-signature size limit. Changed tolerances, look-ahead, state replacement or rewind reset history. Observation owns labels/history/owner indices, never finer physical samples. In automatic gas mode it runs at the selection cadence even if hidden; in the uniform fallback it remains an optional read-only preview.

The uniform engines share the existing 3x3 MYC liquid reconstruction and split material/momentum transport. Exactly absent phases skip unnecessary work; traces are never thresholded away. Their public `State`, `Edit`, `upload`, `download`, `step`, `advect`, `applyGravity`, `project` and sampling APIs remain unchanged. AMR has its own explicit phase-mixture API; it is not a `FluidGrid` facade. Mixture membership/order must be configured before upload. Uniform state masses are mass per cell; AMR converts them once to internal mass densities. GPU operations, including destruction, run on the WebGPU device-owning thread; GL display consumes only prepared colour pixels.

The current CRASHING_WAVE experiment uses user-relaxed detail tolerances 10 velocity, 10 pressure-gradient, 0.5 relative density and 0.5 ingredient fraction; other scenarios retain their own defaults. Finest liquid remains protected. The earlier liquid-integration gate used 0.4/0.4/0.04/0.04 at 512²/100 frames; that historical comparison is not a long-run accuracy guarantee or recovery of the older uniform baseline: [quality/performance sweep](.codex/runs/run0092_20261024_044518/findings.md).

## Editing material at runtime

`beginEdit()` creates a move-only, reusable session over the existing grid. Draw any shape by selecting individual cells; staging does not read or copy the live grid:

```cpp
auto edit = fluid.beginEdit();
edit.reserve(256);
for (int y = center_y - radius; y <= center_y + radius; ++y)
for (int x = center_x - radius; x <= center_x + radius; ++x)
{
    if ((x - center_x) * (x - center_x) + (y - center_y) * (y - center_y) <= radius * radius)
        edit.setCell(x, y, fluid::Phase::Liquid, water_element);
}
edit.commit(); // CPU; GPU commits must run on the device-owning thread.
```

The scene chooses positions, shapes and timing. Keep the chosen cells inside the grid. The grid must outlive its sessions, and `upload()` must have initialized the configured mixtures before a nonempty commit. Stage on one thread at a time and commit between physics/drawing operations; GPU commit needs the device-owning thread. Staging, `reserve()`, `size()`, `empty()` and `clear()` issue no GPU calls. Sessions provide staged writes, not reads of existing GPU cells.

`setCell(x, y, Phase::Liquid/Gas, element)` appends a 16-byte command on the supported native build. With reserved capacity it only appends that record; component lookup and mass calculation happen at commit. Each selected cell becomes entirely the chosen ingredient: its liquid fraction becomes one or zero, its selected component mass becomes phase density times cell volume, and all other liquid/gas component masses become zero. The element must already belong to the selected mixture; if it appears more than once there, the first matching component is selected. Elements present in both phases use the density of the selected phase.

The last queued write to a cell wins. Commit validates the whole batch before material changes: out-of-grid coordinates throw `std::out_of_range`, and a missing phase ingredient throws `std::invalid_argument`. Rejected commands remain queued for inspection/counting or `clear()`. Successful commit clears the commands and retains staging capacity for reuse. Empty commits do nothing; destroying or clearing a session discards uncommitted writes. A session must not be used concurrently with a mutation of its grid or mixture configuration.

Commit preserves current face velocities and pressure prediction history, so replacement material inherits the local flow and the existing divergence-free transport condition. The next physics operation rebuilds stale density/pressure data. This is an explicit material source/sink: replacing gas with water removes the gas mass in those cells; it does not compress or relocate that gas.

Commit sorts only when edits are out of raster order and resolves duplicates. CPU commit writes only the selected cells, using the existing thread pool for large batches once each cell has a unique final replacement. GPU commit packs contiguous row spans; equal adjacent spans merge into rectangles without covering unedited gaps. It uploads only the selected fractions and packed ingredient masses, reusing a staging buffer; there is no readback or full-grid upload. With the scene's four ingredients, 100 distinct edited cells transfer 2,000 bytes of buffer payload. Widely scattered edits still require more upload calls than compact shapes.

## GPU component execution

Uniform `FluidGridGPU` stores four ingredient lanes per float storage-buffer group. Geometric phase fluxes and frozen corrections remain shared by all ingredients; density and colour are derived. WGSL keeps the same split PLIC/momentum equations and outgoing donor bounds. No post-update clipping or renormalization hides drift.

Adaptive `FluidGridAdaptiveGPU` stores component-major arrays only at the committed patch resolutions, plus covered coarse cells and numerical scratch. Shared hierarchy/ghost/transfer/pressure metadata contain geometry, not a CPU physical copy. Ghost fills, restriction, conservative refinement, face exchange, pressure coefficients, both solvers and reductions run on GPU. Regrid clears buffer-binding caches so obsolete hierarchies are released. Cached bindings retain their buffer handles as well as the bind group, preventing browser handle reuse from selecting stale storage.

Pressure execution caches a compact ghost list and direct patch jobs at each layout. Operator jobs cover contiguous valid cells; red/black jobs address only their selected colour, including odd-width patches. Bulk kernels use 128x1 workgroups. Geometry uses four component-major planes (flags, stride, diagonal-recipe offset, interpolation-recipe offset), with boundary/interpolation records stored separately in the same buffer; offsets in dispatch parameters are bit-preserved integers. This replaces the old 24-word per-cell record without changing stencil arithmetic, colour/ghost order, compensated pressure or the shared coarse cycle. A two/four-sweep weighted-Jacobi experiment increased total solve cost and was removed; red/black remains the production smoother. [Execution comparison and validation](.codex/runs/run0111_20261025_164947/README.md).

Accumulated GPU pressure uses explicit high/low float planes; its low plane begins at `width*height` and is cleared with the high plane on upload/regrid. Transport, coefficients, all Krylov vectors and multigrid work remain single precision. Compensated pressure updates, boundary interpolation, operator/flux evaluation and selector pressure differences retain corrections below one float ULP. If a float GMRES pass reaches its estimate before the recomputed residual meets the requested absolute active-cell L2 target, another correction uses that true residual within the same projection and the same total iteration cap. This preserves projection cadence and tolerance. The 512² wave requires this representation: rounding a converged CPU pressure to one float already exceeds its `1e-3` L2 target. See the [scale regression evidence](.codex/runs/run0101_20261025_webgpu/pressure-stage.md).

`FluidCoarseningGPU` evaluates the same bounded reconstruction, independent MAC-face error, pressure impulse, protected liquid, swept look-ahead and quiet history as the CPU preview. Only compact tile requests and summary counts return for the shared clustering step. Optional labels/diagnostic errors are observation output. Assessment scratch is not a hidden fine simulation.

The CPU implementation remains the readable numerical reference. Float and double trajectories can diverge near limiter branches, so compare actual divergence, conservation, local volume error and visuals separately. Uniform and adaptive engines retain different momentum discretizations; turning adaptivity off uses the same AMR engine uniformly fine, not the older uniform engine.

## AMR numerical contract

Preserve the coupled algorithm below when optimizing it. Chosen physical cell sizes and the multigrid hierarchy used to accelerate pressure are distinct; retain useful intermediate solver levels. [Current selection and observation rules](#current-cpu-experiment-and-uniform-engines) cover quiet-history padding, committed-state reads and scene ownership.

`FluidGridAdaptive` uses project-owned regular 2D patches, cached boundary exchange, conservative restriction/refinement and the source-derived composite pressure solver below. The application builds and runs without AMReX; only the separate `reference/` project links it. Gas-only ingredient transport reconstructs a bounded linear plane and traces it back half a step in both directions before forming each ingredient flux. Momentum uses the summed mass flux and existing donor cell velocity; it remains first order so this step does not also replace bulk-flow advection. A common mixture limiter preserves summed ingredient volume. Material limiting is independent of momentum. For refinement and coarse ghosts, momentum is the parent velocity times the bounded density plane plus a separately limited, zero-mean linear residual. Corner-density inequalities bound velocity by neighbouring extrema without flattening material. This preserves parent momentum and constant velocity across density changes. `FluidLinearReconstruction.h` defines the spatial plane, mirrored by the shared WGSL in `FluidLinearReconstructionShaders.h`; `AmrTransfer2D` applies it to the coarse/fine stencil. New fine averages and rendered coarse footprints use that same plane, without persistent fine samples. Two ghost layers provide the slopes of face donors; the slope field is derived transport scratch, not another physical state. The full pressure-coupled integrator is not claimed to be second order in time.

Fine face velocities remain independent. Fine ingredient and momentum fluxes are averaged onto the coarse face before divergence updates, so both levels exchange the same mass. On a single resolution, `stableTimeStep()` limits each donor's summed outgoing face velocities to a Courant number of .45, using that level's actual cell width. This avoids combining distant horizontal/vertical extrema and protects bounded linear donors up to twice their mean. Mixed-level hierarchies retain the previous `.45 / max_level((max_abs_u + max_abs_v) / dx)` bound: twice-reconstructed coarse/fine donors and opposing fine-face flows require separate treatment before using a local join bound. Pressure retains the upstream composite operator and averaged MAC correction to cell momentum. [Local-CFL validation and limits](.codex/runs/run0095_20261024_144010/findings.md).

`AmrPressure2D` owns both pressure paths. Differing ingredient densities use extracted GMRES+MLMG; equal-density mixtures use standalone MLMG with normalized BiCGStab at the bottom and upstream's smoothing fallback. The equation, warm pressure impulse, boundary conditions, 200 gas / 2,000 liquid iteration ceilings and composite face corrections are preserved. GMRES uses absolute L2 tolerance equal to the requested maximum-divergence tolerance, a stricter stopping target; standalone MLMG checks the maximum residual. Final actual active-cell divergence remains authoritative. The per-layout adapter copies current coefficients/RHS/warm pressure to retained solver arrays and corrected faces back; these costs remain inside projection/regrid timings. Production has no backend selector. The upstream engine is isolated in `reference/amrex/`, namespace `fluid::reference`.

Each `step(dt)` holds the previously projected face velocities fixed while CFL-subcycling conservative material/momentum transport. Ghost fill, flux synchronization and restriction still occur within each transport substep. The stability bound is computed once because the advecting faces stay fixed. After transport, apply damping over the full `dt`, rebuild the predictor with the full force impulse and updated density, and project once. The caller's `dt` therefore controls force/pressure temporal resolution (the wave uses .016 seconds); transport subdivisions alone do not resolve rapid force changes. Regrid restoration remains a separate required projection. This temporal split follows the old uniform engine's scheduling and does not claim identical trajectories to the previous every-substep projection. [Cadence validation and visual comparison](.codex/runs/run0093_20261024_135203/findings.md).

Projection measures actual predictor divergence first: if it already meets the **same requested tolerance**, pressure correction is zero and expensive solver preparation can be skipped. Otherwise the projected-minus-predicted face difference supplies the momentum correction without calculating the pressure flux twice. Momentum advection remains first order; the material reconstruction above does not establish high-order accuracy for the complete integrator. Clouds/vorticity can still diffuse. At loose scene tolerance (`1e-3`), small local volume-closure errors accumulate despite global ingredient conservation; tight tests and loose cost controls are reported separately.

Each level owns component-major patch arrays with two conserved ghost layers, avoiding a separate full-state copy. Cached `AmrBoundary2D` recipes read current same-level valid cells or interpolate current coarse state, with even material/tangential and odd normal-momentum reflection at walls. They write ghosts only. `AmrFaceSync2D` synchronizes duplicate faces, and cached `AmrTransfer2D` intersections average fine cells/faces conservatively. Regrid rebuilds these geometry plans; uploads/direct valid-state edits require no invalidation. The upstream comparison poisons old ghosts and checks refill, walls/corners, equal/unequal densities, multiple ingredients and layout changes.

`regrid()` transfers native conserved fields. Fine overlap is copied exactly, merging averages down, and new fine cells use bounded conservative interpolation from the real coarse state. No fine download/upload roundtrip occurs. After a changed layout, call `project(tolerance)` before transport. An identical normalized layout is a no-op. Current direct deep restriction assumes its footprint fits inside a source FAB; merge ratios exceeding `maxGridSize` remain a known limitation ([evidence](.codex/runs/run0124_20261026_111420/README.md#separately-discovered-pre-existing-limitation)). Scene default64 covers the supported maximum width32. The engine supports arbitrary gas ingredients/densities, closed slip walls and no subcycling between levels. The gas-only constructor rejects liquid at upload; the two-phase overload accepts liquid and gas mixtures, storing their ingredient lanes in that order. Automatic 1x1/2x2/4x4/8x8/16x16/32x32 layout selection is implemented; automatic liquid coarsening and sizes beyond 32x32 still need their own agreed steps.

When liquid ingredients are configured, transport uses the uniform engine's MYC/PLIC geometry with directional splitting and frozen Weymouth-Yue ingredient/momentum corrections. `FluidInterfaceGeometry.h` shares the geometric formulas between both engines. Each phase's ingredients move with its geometric volume flux; momentum uses their combined mass flux. Fine fluxes are averaged down before each directional update. Corrections cancel for exactly divergence-free faces; with finite solver tolerance, record residual mass-budget error separately from near-roundoff volume closure. The smaller phase is reconstructed directly so a tiny gas sliver is not obtained by subtracting nearly equal liquid/total fluxes. No post-update mass clipping or normalization is used. The interface/phase volumes are derived from conserved ingredient masses; no fine physical copy is retained. Gas damping affects gas-only cells; pressure couples all materials. The AMR cell-momentum discretization remains distinct from the older uniform engine's staggered momentum, so matched AMR fine controls and older-engine visual controls answer different questions.
The [source map and numerical contract](reference/engine/README.md) identify the retained upstream algorithms and license. The normal application manifest/build has no AMReX dependency, include, linkage or initialization. `reference/CMakeLists.txt` separately builds pinned AMReX/Hydro and the AMReX-backed reference adapter. Its project-owned interpolation and gas reconstruction use the same selected material/momentum policy; pinned AMReX/Hydro sources remain unchanged. Native Windows uses LLVM OpenMP; the complete CPU library also builds without OpenMP or Bitloop through `reference/engine/CMakeLists.txt`. The WebGPU port preserves this contract; its current validation status lives in CURRENT_WORK.

### CPU extraction validation

`FluidExtractionTests` in the optional reference project compares clustering, patch splitting, poisoned-ghost refill, regrid, transport and both pressure branches through six levels. On identical evolving inputs, the tested transfers/transport match exactly and projected fields agree within 3e-14 relative error. `FluidPressure2DTests` retains fourteen composite-operator/cycle/solve/flux oracle cases, including density contrast and GMRES restarts. Production `FluidRefinementTests` and `FluidCoarseningPreviewTests` use only our engine. `liquid-short` caps the mixed-ingredient selection fixture at 96 physical steps.

[Complete CPU extraction evidence](.codex/runs/run0100_20261024_cpu_extraction/findings.md): current cloud-free 512² CRASHING_WAVE, max32, two 60-frame pairs. Total including setup/copies/selection/regrid averages 20.73 -> 13.06 s (37% lower); transport 28% and complete physical-step projection 48% lower. Material and actual-grid captures inspected at 1/20/40/60; extracted liquid stays fine and surfaces are close. Layout histories and tiny droplets differ with accumulated roundoff, including between upstream repeats. This comparison establishes short-run extraction parity/cost, not a win over the older optimized uniform engine or a GPU gain.

### Scenario captures and validation

`FluidRefinementTests reconstruction` checks moving velocity extrema over smooth composition, conservative averages, material volume identities, velocity bounds, constant velocity at density contrast1/10/1000, and the material/velocity representation contracts through width32. `FluidAmrWebGPUTests reconstruction` requires an unchanged material image to remain bitwise identical under moving momentum extrema and checks CPU/GPU transfers, total momentum and constant velocity across mixed layouts. The existing selection suite verifies estimator/reconstruction parity.

### Prescribed-pressure uniform boundary

CPU wave scenarios keep the tested `top_ambient` API with zero pressure and scene gas fractions. Inflow supplies that composition and zero donor velocity; outflow carries interior ingredients/momentum. Exchange counters track the open-system budget. Adaptive gas is closed and does not substitute atmosphere with a reservoir. These are explicit physical models.

## One physics substep

`FluidGrid::step()` accepts an optional fourth argument, `FluidGrid::StepTimings*`, reporting transport, forces and complete pressure-projection milliseconds. A null pointer performs no clock reads. Dev-mode scene traces include stage timings alongside complete physics time.

Read `FluidGrid::step()` first:

```cpp
advect(dt);
dampGasVelocity(dt); // CPU, optional; zero rate returns immediately
applyGravity(dt);
return project(dt, max_iterations, divergence_tolerance);
```

1. **Transport material and momentum:** reconstruct interfaces, calculate liquid-volume transfers, transport component masses and carry both momentum components through X, then Y. After each material pass, recover velocity by dividing momentum by the new face density. Repeat with smaller transport steps when needed to limit outflow.
2. **Apply forces:** the CPU optionally damps gas-only velocities, then gravity adds acceleration to vertical faces, including the optional open face. Damping before gravity preserves the hydrostatic background. Both materials receive the same gravitational acceleration; density affects their pressure response.
3. **Project pressure:** rebuild density coefficients from the current component masses, apply the selected closed/open boundaries, solve for pressure and correct velocity until cell divergence meets the requested tolerance.
Transport uses the previous substep's projected velocity. The scene starts with zero velocity, which already satisfies incompressibility. An experiment that directly changes velocities must project them before transport. The final projection handles the transported state and gravity, preparing the next substep.

`sceneProcess()` uses the selected scenario's `frame_time` and divides it into `ceil(frame_time * 60)` equal steps: three for the cosine scenario, five for the crashing wave. It calls `fluid.step(step, 2000, 1e-3)` for the uniform CPU wave path; AMR gas uses its own ordered step at the same substep interval. The CPU regression reference retains its double-precision `1e-8` checks; the scene uses the same explicit float-compatible target for comparisons. The engine advances exactly the time passed to it; it does not know about frames or recording. Older measurements below used different timesteps; compare timing only with matched timestep and simulated duration.

On failed final projection, `step()` returns an unconverged result after transport and gravity have already run. It does **not** roll back material, velocity or pressure. The scene pauses and reports the failure rather than continuing with that state. A zero timestep leaves state unchanged.

## Material and momentum transport map

| Function | Question it answers |
| --- | --- |
| `liquidArea` | How much liquid lies inside this local rectangle, given a dividing line? |
| `interfaceNormal` | Which way does the line face, estimated from neighbouring fractions? |
| `interfaceOffset` | Where must that line sit to enclose this cell's liquid fraction? |
| `rebuildInterfaces` | What are the current normal and offset for each mixed cell? |
| `liquidTransferX/Y` | How much liquid lies in the outgoing strip beside this face during this substep? Returns a signed fraction of cell volume, already accounting for time |
| `rebuildTransfersX/Y` | Cache liquid-volume transfers through each face for this pass |
| `componentMassTransfer` | How much of one ingredient's mass follows its phase's transferred volume? |
| `rebuildComponentTransfersX/Y` | Cache one ingredient's transfers and accumulate total mass transfers for momentum |
| `freezeComponentCorrections` | Select the phase and fix ingredient/momentum split corrections in small contiguous blocks before the X/Y pair |
| `advectComponents` | Update each ingredient using its transfers and the frozen correction |
| `rebuildDensity` | What cell density follows from total component mass divided by cell volume? |
| `rebuildMomentum` | What momentum density belongs to each face velocity? Uses the average density of the two neighbouring cells |
| `momentumTransfer` | How much momentum crosses a boundary? Mass transfer times donor velocity |
| `advectMomentumX/Y` | Carry both momentum components in this direction using the cached mass transfers and matching split corrections |
| `recoverVelocity` | Divide momentum by current face density and write `next_u/next_v` |
| `advect` | Coordinate material and momentum through successive X/Y passes and CFL substeps |

Local geometry uses a unit square per cell; no local-coordinate fields are stored. `liquid_fraction` tracks combined liquid geometry; `liquid_mass` and `gas_mass` track ingredient masses. Their occupied volumes stay consistent through the shared transfers. Interface arrays are rebuilt working data. `split_weights` are numerical correction flags fixed across both passes, not rounded material fractions. Pure gas/liquid cells bypass interface-area calculations. The shared geometric boundary is still needed even though several miscible ingredients can occupy either side.

During the entire `advect(dt)` call, `u/v` remain fixed for material transport and momentum corrections. `next_u/next_v` hold the evolving donor velocities; momentum is updated in place because no loop reads a neighbour's momentum. After each fraction swap, density and working velocity are rebuilt. The velocity buffers swap only after all transport substeps finish. Frozen correction weights are chosen separately for each X/Y pair; their combined contributions vanish for exactly divergence-free transport velocity.

The current method always processes X before Y and uses first-order donor velocities for momentum. It preserves sharper interfaces and couples mass/momentum transport, but numerical damping remains. It does not establish smooth droplets, realistic splashes or complete liquid behaviour.

In both engines, `interfaceNormal()` reads the eight surrounding fractions once. Three-cell column/row totals estimate the surface slope; a weighted Youngs gradient provides an alternative near corners and thin features. MYC selects the dominant height direction and compares the two slope estimates. `interfaceOffset()` still positions the chosen line to match the original liquid volume. This changes the reconstructed angle, without filtering fractions or adding a force. The GPU performs this work inside its existing mixed-cell reconstruction pass, with no additional textures or passes. For the underlying method, see [Basilisk's 2D MYC implementation](https://basilisk.fr/src/myc2d.h).

## What the existing optimisations do

These preserve the current pressure equation and the outer PCG algorithm. Multigrid changes the preconditioner; the other optimisations change the amount of work or its arrangement. Floating-point rounding and stopping iterations can affect the trajectory within the requested accuracy.

| Optimisation | Plain meaning | Where to look |
| --- | --- | --- |
| Reused vectors | Keep allocated working memory between solves | `project` and private buffers |
| Explicit cache invalidation | Reuse density and pressure coefficients until component masses change; direct CPU edits call `invalidateCaches()` | `upload`, `advectComponents`, `rebuildDensity` |
| Momentum/donor initialization | Copy initial donor velocity while building momentum, avoiding a density rebuild and multiply/divide round trip | `rebuildMomentum` |
| Pressure prediction | Use the last two pressures to guess the next one; rebuild the residual against the current system | Start of `solvePressure` |
| Lazy multigrid setup | Rebuild a stale hierarchy only after prediction leaves a residual that needs solving | `solvePressure` |
| Cached inverse diagonal | Compute each cell's diagonal reciprocal when density changes rather than divide every CG iteration | `rebuildPressureCoefficients` |
| Multigrid V-cycle | Smooth local errors, solve broad errors on smaller grids, interpolate corrections back and smooth again | `PressureMultigrid::cycle` |
| Density-aware coarse weights | Combine pressure conductances in series and parallel instead of averaging away density barriers | `PressureMultigrid::coarsen` |
| Reused coarse factorization | Factor the smallest system when rebuilding a stale hierarchy; reuse it in every V-cycle | `factorCoarsest`, `solveCoarsest` |
| Zero halo | Zero wall weights and a padded border remove boundary branches from multigrid stencils | `PressureMultigrid::Level` |
| Interior/boundary split | Interior cells always have four neighbours; process them without boundary checks, then handle walls separately | `applyPressureOperator` |
| Row pointers | Locate each row once, then walk along it instead of reconstructing flattened indices | Interior operator loop |
| Fused updates and statistics | Update pressure/residual and measure the residual in the same pass | `updatePressureAndResidual` |
| Fused stencil/dot product | Accumulate CG's denominator while applying the pressure operator | `applyPressureOperator` |
| Fused RHS/true-residual statistics | Accumulate compatibility or convergence statistics while forming those fields | `project`, `rebuildPressureResidual` |
| Fused preconditioner reduction | Remove the correction's mean while accumulating the dot product CG needs | `applyPreconditioner` |
| Four accumulators | Let the CPU work on several independent sums instead of waiting on one running sum | Residual/preconditioner loops |
| Size-aware pressure parallelism | Keep small/coarse grids serial; batch pressure updates, reductions, setup and copies as well as stencils; merge reductions in batch order | `forBatches`, `reduceBatches`, multigrid `forRows` |
| Row-based transport | Traverse complete rows to avoid per-face coordinate division; workers read fixed inputs and write disjoint entries | Transport and interface loops |
| Batched component corrections | Choose phase and its reciprocal once per cell; traverse ingredient arrays in small blocks within one worker dispatch | `freezeComponentCorrections` |
| Equal frame substeps | Avoid tiny remainder timesteps that make pressure prediction less useful | `sceneProcess` |

`applyPressureOperator` defines the equation; `applyPreconditioner` helps CG solve it faster. Mean removal before and after preconditioning preserves symmetry on mean-zero pressures. Both engines expose `PressurePreconditioner::{Multigrid, Diagonal}` and a `pressure_preconditioner` member. Set `grid.pressure_preconditioner = decltype(grid)::PressurePreconditioner::Diagonal` to compare with the original method without changing the scene's backend declaration.

Read `PressureMultigrid::cycle()` for the sequence. Each level groups roughly 2x2 cells until at most 64 remain. Four red/black Gauss-Seidel sweeps reduce local error; `restrictResidual` passes the remaining error down. The smallest system fixes one pressure, solves by Cholesky and removes the arbitrary constant. `prolongCorrection` interpolates the correction back, followed by four sweeps in the reverse colour order. Restriction is exactly the transpose of prolongation. These choices make each application a fixed linear symmetric positive preconditioner, as ordinary PCG requires. Coarse conductances approximate the fine system; the fine-grid equation and its final convergence checks remain authoritative.

The hierarchy's dimensions, interpolation maps and buffers are reused. Density-dependent conductances and the small factorization rebuild when masses have changed and a solve actually needs the preconditioner. Independent cell/row updates use `detail::updateWorkers`: below 32,768 work items stay serial, medium batches get roughly 8,192 items per worker, and larger batches retain the eight-worker cap, bounded by the shared pool. This prevents a 32K block from losing all parallelism when a uniform grid is split. Reductions retain their original 65,536 threshold and batch order; changing their grouping can change floating-point rounding and stopping iterations. Multigrid retains its original four workers on medium levels and eight above about one million cells, with small/coarse levels serial. Red/black smoothing retains a barrier between colours and four symmetric pre/post sweeps. The fine pressure equation, true-residual verification and final divergence checks are unchanged.

True-residual verification and the final divergence check are correctness checks, not optional performance overhead. A small internal CG residual alone does not prove that the final velocity meets the requested divergence tolerance.

## WebGPU execution and display

`FluidSimEngineGPU` links the optional `bitloop::webgpu` component. FluidSim's manifest requests `bitloop[webgpu]`; managed tooling selects the component and Dawn dependencies in source and package builds. FluidSim deploys the runtime when built as the root executable; Gallery handles its composite executable. Native uses Dawn; browser uses the matching Emdawnwebgpu package and the same C++/WGSL. FluidSim enables cooperative Asyncify waits for its browser worker. Generic device setup, raw wgpu handles and reusable mapped readback are documented in Bitloop's `docs/webgpu.md`; simulation dispatch and numerical policy stay in FluidSim.

Create, command, poll and destroy a device on one thread. The scene owns it on the simulation worker. Numeric tests need no OpenGL context. Rendering uses Bitloop's existing OpenGL/NanoVG/ImGui backend. The worker prepares `materialPixels()` on WebGPU; the render thread uploads the derived fields and shades them in GLSL. `colorPixels()` remains available as a raw-colour observation API. No WebGPU handle crosses into the GL render thread.

`FluidMaterialPixels` holds ingredient volume fractions in RGBA groups, with liquid ingredients first and gas ingredients afterward. Each group is one width-by-height layer; groups stack vertically in `u_fractions`. The contiguous readback appends one scalar width-by-height liquid-coverage plane, uploaded separately as `u_liquid`. Uniform coverage comes directly from committed `liquid_fraction`, independently of mass-derived composition. AMR geometry comes from its conserved liquid ingredient volumes; coarse samples use the existing bounded display reconstruction and covered cells do not contribute twice. These are observation-only display samples, not additional fine physical state. The WebGL engine derives its fraction atlas on the GPU and supplies its current liquid texture without a CPU readback.

`FluidShader.h` owns `fluid_shader_src`. Its `ingredientFraction(cell,k)` and `liquidFraction(cell)` helpers support exact neighbour reads with clamped boundary coordinates. `ingredientColor(k)`, `ingredientElement(k)` and `liquidIngredient(k)` use a palette and the actual engine mixture counts. Palette RGBA holds RGB colour and ElementId; ingredient slots are not ElementIds, and an element in both phases keeps two distinct slots. Adaptive gas-only scenes supply their actual gas-only mixture. `materialColor()` remains the fraction-weighted colour baseline. The enabled depth-shading pass replaces only the liquid's colour contribution with a light/cool surface tint that fades exponentially to a darker ingredient tint. Alpha stays one; no scene background is sampled. Resolution/decision overlays remain separate. Raw `material` captures retain the unshaded mixture view; `appearance` captures show shading without diagnostic overlays.

`FluidLiquidDepth` prepares the approximate nearest-gas position at grid resolution using a seed pass and jump flooding (halving neighbour offsets, then one extra unit-offset pass). Cells with liquid fraction below .5 seed gas; domain walls never seed it. This 50% contour is a visual approximation, not an interface reconstruction or physical optical path. Bubbles brighten nearby liquid, and a tank with no gas receives the deep tint everywhere. RGBA8 stores two normalized 16-bit seed coordinates (x low/high, y low/high, 65535 reserved for invalid); blending, dithering and sRGB conversion are disabled while packing. This avoids an extra float-render-target requirement in WebGL2. The map and its two ping-pong surfaces are display scratch only, owned/destroyed on the render thread; added work belongs to rendering, with no simulation/performance claim. The Liquid appearance panel exposes Depth shading, Tint depth (32 cells initially) and Deep brightness (.16 initially). Turning the effect off restores the flat colour baseline.

WebGPU packs fractions and coverage into one buffer/readback without downloading velocity, pressure or full physical state. The transfer has `4*ceil(ingredient_count/4)+1` floats per cell (one zero RGBA layer for an empty catalogue); four ingredients use 20 bytes per cell versus the earlier colour image's 16. This change enables shading experiments and makes no performance-improvement claim. Its cost remains in the existing display/readback timing.

The scene reports completed physical-step cost, selection and regrid, and the display-field/readback bridge. Per-phase GPU timings are unavailable without additional synchronization; they are not reported as enqueue-time measurements. Full diagnostic state downloads are explicit and excluded from simulation timings. Setup and regrid must be included in throughput comparisons. `synchronize()` is available for standalone completed-work measurements.

Native FluidSim opts into Bitloop's optional `WebGpuDevice::Options::cache_directory` using `SDL_GetPrefPath("bitloop", "FluidSim")/webgpu-cache`. The first use compiles shaders; subsequent launches reuse Dawn binaries. Missing/damaged/unwritable cache files fall back to compilation. Browsers retain their own cache. The project-owned `tooling/ports/dawn` overlay fixes an unordered D3D12 binding vector in the current Dawn cache key, retaining its version and registry baselines. See [overlay details](tooling/ports/README.md). Material, velocity and pressure refinement checks are separate kernels sharing existing observation storage, reducing cold compilation without changing thresholds, protected liquid, look-ahead or history. No extra physical state is retained.

The uniform solver is wholly GPU, including tiny Cholesky. The former `cpu_pressure_cells` option and GL texture getters were removed. Adaptive pressure uses shared geometry plans, grouped conservative reflux, red/black dispatch barriers and GPU Krylov state/reductions. Prescribed quality settings and true residual/divergence checks remain authoritative.

Adaptive pressure reductions use 128-thread workgroups, four contiguous input bands per chunk, a grid stride capped at 1024 groups, and one final workgroup. Shared-memory sums/maxima retain active/covered masks, ordered level accumulation and nonfinite flags; partial scratch is bounded and reused. `FluidPressureWebGPUTests reductions` checks poisoned inactive cells, odd tails, six levels, a 1031-square grid-stride norm and failure reporting; `all` includes those cases. Adaptive devices now request optional subgroups and use subgroup sums/maxima for scalar and four-product reductions when supported, retaining the shared-memory fallback. Elected local slots and active subgroup lane counts avoid assuming a local/subgroup index mapping. Uniform devices are unchanged. Both paths pass; two matched 50-frame comparisons show no meaningful total-frame gain (512 85.09 -> 84.02 ms, 1024 191.99 -> 192.96 ms, within run variation). Small isolated reductions improve ~5%; million-cell reductions do not. [Subgroup implementation/visual/performance evidence](.codex/runs/run0116_20261025_210256/README.md); [DXC packaging](../../bitloop/.codex/runs/run0010_20261025_203347/README.md). [Desktop scheduling comparison](.codex/runs/run0115_20261025_195525/README.md); [earlier portable/browser validation](.codex/runs/run0107_20261025_145023/README.md).

GMRES now stores its basis in tiles of up to four scalar planes per AMR level, capped by the device's storage-binding limit. Normalization publishes each vector once; two rolling fields replace the separate per-vector working fields. Batched products and updates retain both orthogonalization passes: all products in a pass use the unchanged candidate before subtraction. The final linear combination uses the same tiled storage. Krylov scalars remain on GPU; the host checks completion after each candidate to avoid submitting additional preconditioners after convergence. True-residual verification, caps, breakdown reporting and compensated pressure are preserved. [Desktop measurements and numerical checks](.codex/runs/run0108_20261025_150535/README.md).

The GMRES base V-cycle fuses a complete small tail into one 128-thread workgroup when all coupled cells/halos fit two 2048-float shared planes (16 KiB). Static boundary/transfer recipes and GPU-packed face/diagonal coefficients preserve the existing two pre/post sweeps, eight bottom sweeps, ghost refill order, averaging and injected corrections. Direct residual evaluation during restriction removes the scratch plane. Coefficients refresh lazily after `setCoefficients()`; larger/unsupported tails and the standalone BiCGStab-bottom path retain ordered generic execution. `AmrPressureGPUCoarseShaders.h` holds these kernels. Pressure tests cover coefficient refresh, nullspace and an oversized odd-grid fallback; direct generic/fused comparison is bitwise equal on 23,280 tested values. [Desktop timings,50-frame visual/health checks and remaining limits](.codex/runs/run0109_20261025_153440/README.md).

Physical-level pressure stencils use cached 128-thread patch jobs and compact ghost recipes. The operator can return `A(p)`, `rhs - A(p)`, or update an in-place residual, avoiding separate residual vector passes and a scratch field. Composite application reuses its freshly filled pressure ghosts during reflux; the descending preconditioner reuses the coarse solution boundary and refreshes the fine solution explicitly. Red/black fills and public operation boundary preparation remain required. The residual formula and coarse/fine ordering follow the pinned AMReX routines; combining the stencil and residual update is a WebGPU execution adaptation. [Source comparison, matched timings and visual checks](.codex/runs/run0113_20261025_174035/README.md).

Pressure restriction/reflux dispatch compact unique destinations, preserving duplicate-face last-recipe behavior and each interface sum's order. Interpolation and Krylov updates reuse valid-patch jobs; contiguous bulk clear/copy kernels remain. The preconditioner writes directly into its caller's float output and swaps held/correction workspaces. Only the first boundary fill immediately after clearing an entire homogeneous correction is omitted; later red/black updates remain mandatory. These AMReX-aligned execution changes preserve the numerical contract but produce only small measured gains, not adaptive-over-uniform success. [Retained code, source map and visual validation](.codex/runs/run0115_20261025_195525/README.md).

A limited experiment packing pressure work vectors across levels was removed: it cut pressure launches by 7% but improved the primary 1024-square evolving case by only 1–2%, with slight regressions in a three-level case. Production retains separate level buffers; no view/packing API remains. This did not test a complete packed Krylov basis/reduction path. [Experiment and restoration evidence](.codex/runs/run0114_20261025_183352/README.md).

### Uniform backend measurement

Native `FluidUniformBenchmark` compares WebGPU and WebGL using the same cloud-free wave, four ingredients, damping 2, .016-second steps and 1e-3 divergence target. `full 16 512` times completed updates plus colour transfer after four warmup frames; `profile 16 512` separates transport/forces/pressure with additional completion barriers. WebGL's final cutoff argument defaults to1024; zero tests fully GPU pressure. Startup and actual canvas drawing are excluded. For example: `FluidUniformBenchmark webgpu full 16 512` and `FluidUniformBenchmark webgl full 16 512 1024`.

Shader vector-buffer helpers use explicit component lanes so scalar consumers can discard unused work. The measured short native comparison fell from 75.0 to 52.7 ms/frame; WebGL measured 46.2 ms. This is not an adaptive or browser speed claim. [Diagnosis, controls and validation](.codex/runs/run0103_20261025_uniform_performance/README.md).

Buffer channel counts are now WGSL pipeline overrides, with cached variants for actual scalar/vector layouts. Uniform multigrid executes compatible small coarse hierarchies in one 256-invocation workgroup (16,320 bytes shared memory), preserving all levels, transfer weights, five pre/post sweeps and the tiny direct solve. Power-of-two coarse bases up to 1024 cells, at most four remaining levels / 1360 cells use this path; other shapes retain separate dispatches. This is pressure acceleration only: every uniform simulation cell remains 1×1. Convergence policy and quality settings are unchanged. Two short matched 512² rounds average 56.49 → 40.45 ms/frame versus WebGL 43.93 ms, including colour transfer. Focused numerical gates and native wave images pass; rounding differs, so this is not bitwise equivalence or a new long-time/adaptive/browser guarantee. [Current evidence](.codex/runs/run0104_20261025_uniform_pressure/README.md).

The optional Desktop test target FluidPressureWebGPUReference replays trusted frozen pressure inputs against our executor; reference/pressure_gpu builds the corresponding pinned native AMReX GPU utility separately. ## Regression baseline

`FluidDisplayTests` creates a hidden GL context and checks the actual material shader/helpers, texture row/layer order, ElementId mapping, independent uniform liquid geometry, 0/4/7/18 ingredients, uniform CPU/WebGPU/WebGL agreement, mixed-level bounded AMR display, unchanged physical state and the retained raw-colour/ambient display paths. It links the WebGPU engine and deploys its runtime. These are display checks, not an evolving-performance benchmark.

Enable `FLUIDSIM_BUILD_TESTS=ON` when configuring, build `FluidSimTests`, then run:

```text
ctest --test-dir <build-directory> -R "^FluidGridTests$" --output-on-failure
```

On Windows, configure/build from a Visual Studio developer shell. The test executable needs the same vcpkg runtime DLL directory on `PATH` as the application (`<build-directory>/vcpkg_installed/x64-windows/bin`).

GPU cases cover hydrostatics, odd/thin projection, CPU comparisons, all four diagonal directions, nonuniform momentum transport, tiny interface remnants, sharp slabs, exact pure-material preservation, zero-time/failure handling. GPU multigrid algebra tests cover odd/thin/high-contrast grids through 513x257, including the larger-grid polynomial smoother. Additional cases protect 512x512 default-budget convergence, the one-iteration cap and exact cached-versus-refreshed CFL parity. Common-API tests exercise upload/download, zero/reset behavior and actual display pixels for both types, including an empty catalogue. Component comparisons cover liquid-only, gas-only, 4, 7 and 18 ingredients, empty fields, differing densities, an element in both phases, and populated ingredients beyond the first sixteen. A 512x512 regression exercises the formerly failing vanishing-sliver case. Both engines' legacy fixtures explicitly populate component masses through `tests/FluidTestSetup.h`.

## Small future milestones

Choose **one** with the user; the list is not a commitment to implement everything. Each new feature should add one clear experiment or focused regression before another feature is added.

| Possible milestone | Small demonstration / acceptance case |
| --- | --- |
| General 2D acceleration | Uniform gravity reproduces today's result; a smooth custom field moves fluid in-plane. Mandelbrot depth can generate that field; it adds no water-depth variable |
| Colour labels | Two colours travel with the same fluid properties. Colour alone does not require a new physical element or pressure solve |
| Material-dependent surface tension | A droplet tends towards a round interface when enabled; zero tension preserves the no-tension case |
| Omit eligible ambient cells | Use the per-cell mask with irregular boundaries, preserving the fine-cell resolution and accounting for material/momentum exchange; compare against the fully simulated reference |
| Trapped gas pockets | A sealed bubble resists collapse through a pocket-pressure/volume model or resolved gas; connection to the exterior changes its treatment |

Keep the current engine concrete until a second working case needs an abstraction. Start generalising forces where they are applied, material properties where coefficients are built, and exterior conditions where pressure boundaries are imposed. Avoid a feature registry, automatic physics selection or a collection of unused switches now.

Execution choices may eventually become automatic from grid size and profiling. Whether air is a real simulated fluid, an ambient-pressure exterior, or a trapped pocket remains a modelling choice: those cases have different physical behaviour.
